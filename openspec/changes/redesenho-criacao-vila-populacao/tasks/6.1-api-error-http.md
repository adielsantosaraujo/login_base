## Objetivo

Implementar tratamento de erros HTTP no cliente com `status` e `codigo`, interceptando respostas da API e extraindo informações de erro do body JSON.

## Contexto necessário

- [design.md — D13 (cliente HTTP / ApiError)](../design.md#d13-frontend-rotas-guarda-e-apierror) — estrutura de ApiError com `status` e `codigo`
  > `export class ApiError extends Error { status: number; codigo?: string }`; mensagem = `dados.erro ?? dados.mensagem ?? 'Erro <status>'`; continua `instanceof Error` (os composables atuais não mudam).
- [design.md — D5 (tabela de códigos de erro)](../design.md#d5-formato-de-erro-com-código) — formato `{erro, codigo}`
- [Arquivo existente: /frontend/src/api/http.ts](/frontend/src/api/http.ts) — cliente HTTP atual

## Arquivos a criar/alterar

- [/frontend/src/api/http.ts](/frontend/src/api/http.ts) — estender com tratamento de erros `ApiError`
- [/frontend/src/api/http.spec.ts](/frontend/src/api/http.spec.ts) (novo) — testes com mock de `fetch`

## Notas de implementação

- `ApiError` deve estender `Error` e conter `status: number` e `codigo?: string`
- 404 sem corpo → `ApiError` com `status` 404 e mensagem "Erro 404" (erro de rede continua sendo o erro do `fetch`, sem `ApiError`)
- Corpo com `{erro, codigo}` → extrair `message` e `codigo`
- Corpo com `{mensagem}` (formato do contrato do handoff) → aceitar como `message`
- Sem corpo → "Erro 500"
- 401 → manter redirecionamento existente (não quebrar comportamento atual)
- Verificar `instanceof Error` em testes

## Critérios de aceite

- 404 ⇒ `ApiError` com `status` 404
- Corpo `{erro, codigo}` ⇒ `message` e `codigo` extraídos
- Corpo `{mensagem}` ⇒ aceito como fallback
- Sem corpo ⇒ "Erro 500"
- 401 continua com redirecionamento (comportamento preservado)
- `instanceof Error` funciona
