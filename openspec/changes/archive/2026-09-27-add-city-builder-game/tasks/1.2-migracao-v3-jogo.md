# Task 1.2 — Migração V3 do jogo

**Índice:** [tasks.md](../tasks.md) · **Depende de:** — · **Paralela com:** 1.1, 1.3, 1.4, 7.1

## Objetivo
Criar o arquivo de migração Flyway `V3__jogo.sql` que define todas as tabelas do jogo (vilas, prédios, canteiros, sementes, itens, unidades, ordens, batalhas) com constraints, checks e índices conforme especificação em B.2.

## Contexto necessário
- [design.md — Banco de dados](../design.md#13-banco--v3__jogosql) — estrutura das 8 tabelas
- [Flyway setup](/src/main/resources/db/migration) — V1 e V2 já existem; próxima é V3
- `application.properties` com `spring.jpa.hibernate.ddl-auto=validate` — tabelas devem estar prontas na inicialização

## Arquivos a criar/alterar
- [V3__jogo.sql](/src/main/resources/db/migration/V3__jogo.sql) (novo)

## Notas de implementação
Todas as tabelas seguem padrão:
- PK: `bigint generated always as identity`
- Auditoria: `criado_em timestamptz not null`, `criado_por varchar(150) not null`, `alterado_em timestamptz not null`, `alterado_por varchar(150) not null`
- FK para `usuarios(id)` em `jogo_vilas` com `foreign key`
- Enums como `varchar(30)` com `EnumType.STRING` em JPA
- Índice em todo `vila_id` para acesso rápido

Tabelas principais (de B.2):

| Tabela | Colunas chave | Restrições |
|---|---|---|
| `jogo_vilas` | `usuario_id`, `nome varchar(100)`, `comida/madeira/pedra/ferro bigint`, `recursos_atualizados_em timestamptz`, `masmorra_nivel_liberado int` | FK `usuarios`, `unique(usuario_id)`, `check recursos >= 0`, `check nivel 1–5` |
| `jogo_predios` | `vila_id`, `tipo varchar(30)`, `nivel int` | `unique(vila_id,tipo)`, `check nivel 0–5` |
| `jogo_canteiros` | `vila_id`, `posicao int`, `cultivo varchar(30)`, `plantado_em timestamptz` | `unique(vila_id,posicao)`, `check posicao 1–5` |
| `jogo_sementes` | `vila_id`, `cultivo varchar(30)`, `quantidade int` | `unique(vila_id,cultivo)`, `check quantidade >= 0` |
| `jogo_itens` | `vila_id`, `modelo varchar(30)`, `nivel int`, `origem varchar(20)`, `status varchar(20)` | `check nivel 1–5` |
| `jogo_unidades` | `vila_id`, `tipo varchar(20)`, `arma_item_id`, `armadura_item_id`, `status varchar(20)` | FKs itens, `unique` em cada item |
| `jogo_ordens` | `vila_id`, `categoria varchar(20)`, `alvo varchar(30)`, `nivel int null`, `quantidade int`, `arma_item_id null`, `armadura_item_id null`, `iniciada_em`, `conclui_em` | `unique(vila_id,categoria)`, FKs itens |
| `jogo_batalhas` | `vila_id`, `masmorra_nivel int`, `status varchar(20)`, `turno int`, `estado text`, `log text`, `loot text null`, `iniciada_em`, `finalizada_em null`, `version bigint` | índice único parcial `(vila_id) where status = 'EM_ANDAMENTO'` |

## Critérios de aceite
- `V3__jogo.sql` aplicada sem erros em Postgres limpo (V1 e V2 existem)
- Todas as 8 tabelas criadas
- Constraints e checks aplicados (testável via `psql`)
- FKs funcionando (insertar vila com `usuario_id` válido funciona, inválido falha)
- Índices criados (incluindo índice parcial em `jogo_batalhas`)
- Aplicação sobe com `ddl-auto=validate` sem erro
- Migração idempotente (reexecução não falha, é pulada por Flyway)

## Verificação
```bash
make up
./mvnw test -Dtest=LoginBaseApplicationTests
psql -h localhost -U postgres -d login_base -c "\dt jogo_*"  # lista tabelas
psql -h localhost -U postgres -d login_base -c "\d jogo_vilas"  # estrutura
```

Deve listar 8 tabelas; `\d` mostra colunas e constraints; `LoginBaseApplicationTests` valida o schema.
