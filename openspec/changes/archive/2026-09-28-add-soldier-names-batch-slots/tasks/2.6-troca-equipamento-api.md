# Task 2.6 — Troca de equipamento na API

**Índice:** [tasks.md](../tasks.md) · **Depende de:** [1.1](1.1-migracao-v4-unidade-lote.md), [1.3](1.3-slot-equipamento-enum.md), [2.1](2.1-treino-em-lote-servico.md), [2.2](2.2-api-treino-e-unidade-dto.md), [2.3](2.3-morte-libera-slots.md) · **Paralela com:** [2.4](2.4-rota-detalhe-unidade-spa.md), [2.5](2.5-sufixo-nomes-duplicados.md)

## Objetivo
Permitir trocar o item dos slots Arma/Armadura de uma unidade por outro item compatível `DISPONIVEL`, devolvendo o antigo ao inventário, proibido com a unidade em masmorra, via `POST /api/jogo/unidades/{id}/equipamento`.

## Contexto necessário
- [design.md — Decisão D12: Troca de equipamento nos slots Arma e Armadura](../design.md#d12--troca-de-equipamento-nos-slots-arma-e-armadura) — contrato, ordem das validações, efeitos
  > `EquipamentoService.trocar(usuarioId, unidadeId, slot, itemId)` com vila travada (`vilaService.obterParaAtualizacao`). 1) unidade inexistente/outra vila → `RecursoNaoEncontradoException` (404); 2) `EM_MASMORRA` → 422 `UNIDADE_EM_MASMORRA`; 3) slot futuro (`getCategoriaAceita() == null`) → 422 `ITEM_INDISPONIVEL`; 4) item inexistente/outra vila/não `DISPONIVEL`/incompatível (ARMA: `modelo == tipo.armaExigida()`; ARMADURA: `modelo.categoria() == ARMADURA`) → 422 `ITEM_INDISPONIVEL`. Efeito: antigo → `DISPONIVEL`, novo → `EQUIPADO`, `armaItemId`/`armaduraItemId` = novo id. Sem desequipar.
- [spec game-army — Requirement: Troca de equipamento](../specs/game-army/spec.md#requirement-troca-de-equipamento) — cenários (troca de arma com ataque 6→8, armadura couro→ferro, ARCO em Soldado 422, item RESERVADO/EQUIPADO 422, EM_MASMORRA 422, CABECA 422, outra vila 404, morte após troca)
- [CodigoErro.java](/src/main/java/com/example/loginbase/jogo/CodigoErro.java) — acrescentar `UNIDADE_EM_MASMORRA`
- [ErroApiHandler.java](/src/main/java/com/example/loginbase/jogo/api/ErroApiHandler.java) — já mapeia `RegraJogoException` → 422 e `RecursoNaoEncontradoException` → 404 (sem alteração)
- [AcoesVilaController.java](/src/main/java/com/example/loginbase/jogo/api/AcoesVilaController.java) — padrão de ação que devolve `consultarVilaAtualizada`
- [QuartelService.java](/src/main/java/com/example/loginbase/jogo/quartel/QuartelService.java) — padrão de validação de arma/armadura por modelo/categoria
- [MasmorraService.java](/src/main/java/com/example/loginbase/jogo/masmorra/MasmorraService.java) — morte apaga os itens atuais (`atualizarEsquadraoAoFinal`)
- [SlotEquipamento.java](/src/main/java/com/example/loginbase/jogo/catalogo/SlotEquipamento.java) — `getCategoriaAceita()`

## Notas de implementação
- `TrocarEquipamentoRequest(@NotNull SlotEquipamento slot, @NotNull @Positive Long itemId)`.
- Controller: `@PostMapping("/unidades/{id}/equipamento")` → `equipamentoService.trocar(usuarioId, id, req.slot(), req.itemId())` → `ResponseEntity.ok(consultarVilaAtualizada(usuarioId))`. Exige CSRF, como os demais POST.
- Mensagens das exceções em pt-BR, legíveis no Toast (ex.: "A unidade está em uma masmorra; troque o equipamento quando ela voltar.").
- Não criar endpoint de remoção (sem desequipar). Não alterar `MasmorraService`.

## Critérios de aceite
- Troca válida: novo item `EQUIPADO`, antigo `DISPONIVEL`, atributos do `UnidadeDto` refletem o novo item
- Rejeições com o código e status definidos, sem nenhuma mudança no banco
- Morte após troca apaga o item novo e mantém o antigo `DISPONIVEL` (teste em `MasmorraServiceTest`)
- WebMvc: 200 com `VilaDto`; 400 corpo inválido; 403 sem CSRF; 401 anônimo; 422 com `codigo` no `ErroDto`
- `./mvnw test -Dtest=EquipamentoServiceTest,AcoesVilaControllerWebMvcTest,MasmorraServiceTest` passa
