## Notas de implementação

### Métodos públicos `@Transactional`

#### `iniciar(long usuarioId, int nivel, List<Long> unidadeIds) → Batalha`
1. Obter vila travada (`VilaService.obterParaAtualizacao`); sincronizar.
2. Validar nível: `nivel` em 1–5 e ≤ `masmorraNivelLiberado` → `MASMORRA_BLOQUEADA`.
3. Validar unidades: 1–4 distintas, `DISPONIVEL`, mesma vila → `ESQUADRAO_INVALIDO`/`UNIDADE_INDISPONIVEL`.
4. Validar fila: nenhuma batalha `EM_ANDAMENTO` para a vila → `BATALHA_EM_ANDAMENTO`.
5. Carregar unidades e items, construir `EstadoBatalha` inicial (combatentes do jogador, inimigos, turno 1, mapa/obstáculos/spawns de `CatalogoMasmorras`).
6. Salvar `Batalha` com status `EM_ANDAMENTO`, estado/log JSON serializado.
7. Marcar unidades com status `EM_MASMORRA`.
8. Retornar `BatalhaDto`.

#### `consultar(long usuarioId, long batalhaId) → Batalha`
1. Carregar batalha; validar proprietário (vila.usuarioId) → `RecursoNaoEncontradoException` (404).
2. Retornar `BatalhaDto`.

#### `agir(long usuarioId, long batalhaId, AcaoCombate acao) → Batalha`
1. Carregar batalha; validar proprietário → 404; validar status `EM_ANDAMENTO` → `BATALHA_ENCERRADA` (422).
2. Desserializar `EstadoBatalha` do JSON `estado`.
3. Processar ação via `MotorCombate.processar(estado, acao)`:
   - Valida ação (422 `ACAO_INVALIDA` se inválida).
   - Retorna novo estado com log atualizado.
4. Se ação termina a batalha (`MotorCombate.terminou`):
   - Aplicar resultado: `VITORIA` ou `DERROTA`.
   - Se vitória: gerar loot via `GeradorLoot.gerar(nivel, aleatorio)` e aplicar (crédito respeitando capacidade).
   - Liberar próximo nível se vitória: `masmorraNivelLiberado = max(atual, min(5, nivel+1))`.
   - Atualizar unidades: mortas deletadas (e seus items); sobreviventes → `DISPONIVEL` com HP cheio.
   - Gravar `finalizada_em`.
   - Serializar loot em JSON (se vitória) e gravar.
5. Senão (ação durante a batalha):
   - Guardar novo estado + log em JSON.
6. Gravar `Batalha.estado` e `Batalha.log`; incrementar `@Version`.
7. Retornar `BatalhaDto`.

### Persistência
- `Batalha.estado`: JSON serializado de `EstadoBatalha` (combatentes completos com posições, HP, flags).
- `Batalha.log`: texto acumulado, uma linha por evento.
- `Batalha.loot`: JSON de `Loot` (só preenchido se vitória) com recursos em milésimos; DTO exibe inteiros.
- Converter `EstadoBatalha` ↔ JSON via `AttributeConverter` (mesmo padrão de 2.1).

### Liberação de nível
- Após vitória: `novoNivel = max(masmorraNivelLiberado, min(5, nivelDaBatalha + 1))`.
- Se `novoNivel > masmorraNivelLiberado`: atualizar vila.

### Limpeza de unidades e items
- Unidade morta: excluir do banco junto com seus items (FK em cascata? Ou manual com `item.status = EQUIPADO` → delete).
- Unidade sobrevivente: manter items equipados, mudar status para `DISPONIVEL`, restaurar HP cheio.
- Items não equipados (loot): criar novo `Item` com `status = DISPONIVEL`, `origem = MASMORRA`.

### Lock otimista (Batalha)
- `ObjectOptimisticLockingFailureException` → 409 `CONFLITO`.
- Após `agir`, se mudança de outro usuário/sessão → erro; reaplicar ação em novo `agir`.

### Teste `MasmorraServiceTest`
- `@DataJpaTest(includeFilters=@ComponentScan.Filter(type=ASSIGNABLE_TYPE, classes=MasmorraService.class))` contra Postgres (rollback por teste).
- `@Import(JogoConfig, AuditoriaConfig)` e sobrescrever `Clock` e `Aleatorio` com `RelogioAjustavel` e `AleatorioSequencia`.
- Cenários: início válido, vitória com loot e liberação, derrota excluindo unidades/items, ação após fim (422), batalha de outra vila (404).

## Critérios de aceite
- Compilação sem erros.
- Teste `MasmorraServiceTest` passa com: criação com estado correto, persistência do estado/log, vitória com loot aplicado (capacidade respeitada), liberação de nível, derrota deletando unidades/items, ações após fim rejeitadas, isolamento por usuário (404).
- Dados serializados/desserializados sem erros.
- `@Version` incrementado e lock otimista funciona.
